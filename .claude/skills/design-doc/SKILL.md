# 設計書スキル

`.doc/` 配下に、ブラウザで開くだけで読めるHTML設計書一式を作る。
Word/Markdownではなく **HTML** で作る。理由は、ER図をインラインSVGで描け、
画面モックを同じ体裁の中に「実際に動くもの」として同居させられるため。

## 成果物の構成

```
.doc/
├─ index.html              # 設計一式トップ（各文書へのリンクと要点）
├─ db_design.html          # DB設計書
├─ detailed_design.html    # 詳細設計書
└─ mock/                   # 画面モック（実際に操作できる）
   ├─ index.html           # モック一覧と「試せる操作」
   ├─ <screen>.html        # 画面ごと
   ├─ css/app.css          # 本番 web/css/app.css の元になるもの
   └─ js/mock-data.js      # ダミーデータ＋共通ロジック
      js/<screen>.js
```

小さな案件なら `db_design.html` と `detailed_design.html` を1枚に統合してよい。
逆に管理画面・バッチなど独立した領域があれば文書を足す。`index.html` は必ず作る。

## 作業手順

1. **対象を読む。** 移植・リプレースなら移植元のコードを先に読む。
   スキーマ（DDL / モデル定義）、APIのルート一覧、画面のHTML構造の3点は必ず押さえる。
   移植元のパスが実在しない場合は**推測で進めず、実在する候補を提示して確認する**。
2. **章構成を決める。** `references/chapters.md` の標準構成をベースに、
   その案件に無い章は落とし、必要な章を足す。
3. **`assets/doc_template.html` をコピーして書く。** `<style>` ブロックは
   **一字一句そのまま**使う（文書間で体裁が揃うことに価値がある）。
   アクセント色だけ案件に合わせて変えてよい。
4. **モックを作る。** `assets/mock_base.css` をコピーして始める。
   モックの詳細は `references/mockup.md`。
5. **検証する。** 下のチェックリストを全部通す。

## 執筆の原則

**表で書く。** テーブル定義・API一覧・画面項目・区分値は散文ではなく表にする。
カラム定義の表は「カラム / 型 / 制約 / 既定値 / 説明」の5列で統一する。

**「なぜ」を必ず添える。** 選択肢があった箇所には理由を書く。
技術選定、削除規則を CASCADE ではなく RESTRICT にした理由、
FKを張らずに名前をスナップショットする理由 ─ 後から読む人が一番知りたいのはそこ。

**踏む予定の地雷を先に書く。** 実装時に必ずハマる箇所は
オレンジの注意ボックス（`references/writing-rules.md` 参照）で本文中に置く。
末尾にまとめて書かない。読む人はその章を読んでいる時に必要とする。

**移植・リプレースなら「旧実装からの変更点」章を必ず作る。**
そこには機能差分だけでなく、**移植元で見つけた不具合も書く**。
コードを読んだ人にしか書けない情報であり、この章が設計書の価値の中心になる。

**断定する。** 「〜が望ましい」「〜も考えられる」と書かない。
採用した案を書き、採らなかった案は理由付きで「採らない」と明記する。

**日本語で書く。** コード・SQL・識別子は原文のまま。

## 禁止事項

- **`<style>` の外にCSSを書かない。** 文書内でスタイルを揺らさない。
- **モックにCDNを使わない。** ローカルアプリのモックは外部依存ゼロで動くこと。
  設計書本体（`db_design.html` 等）はTailwind CDNを使ってよい ─ 閲覧用だから。
- **モックにダミー画像を置かない。** 図はインラインSVGで描く。
- **スクリーンショットを貼らない。** 画面イメージはSVGかモックの実物で示す。

## チェックリスト

書き終えたら必ず全部確認する。

- [ ] `.doc/index.html` から全文書へリンクが通っている（相対パス）
- [ ] 各文書の目次のアンカーが全部生きている（`#id` と `id=` の対応）
- [ ] HTMLのタグ対応が壊れていない（下のコマンドで検査）
- [ ] テーブル定義の全カラムに説明がある（「—」で済ませていない）
- [ ] API一覧のパスとパラメータが詳細設計の本文と食い違っていない
- [ ] 移植案件なら「旧実装からの変更点」章がある
- [ ] モックをローカルサーバで開き、**主要操作を実際にクリックして確認した**
- [ ] モックがネットワーク遮断下でも動く（CDN参照がない）

タグ対応の検査：

```bash
python .claude/skills/design-doc/scripts/check_html.py .doc
```

モックの動作確認（`python -m http.server` は `file://` では動かないモックのため必須）：

```bash
python -m http.server 8777 --directory .doc/mock
```
