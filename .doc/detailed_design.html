1. システム構成

技術選定と理由

層採用理由
デスクトップ枠pywebview 4.xElectronと違いランタイム同梱が不要。WindowsはOS標準のWebView2を使うため配布サイズが小さい
フロント⇔Pythonjs_api（プロセス内呼び出し）HTTPサーバを立てない。下の枠を参照
DBsqlite3（標準）旧実装の better-sqlite3 と同じSQLite。DBファイルをそのまま読める。追加依存なし
フロント素のHTML/CSS/JS移植元 public/electron-app.* が素のJS。フレームワーク導入は移植の変更点を増やすだけなので行わない
アイコンインラインSVG移植元は Phosphor Icons を unpkg から読んでいた。オフライン動作のため自前のSVGに置き換える

外部ライブラリは pywebview のみ。Flask も HTTP サーバも使わない。

HTTPサーバ方式を採らない理由

移植元は Express でポート3000を開き、Electron からもブラウザからも同じ画面を開ける構成だった。本アプリはアプリとしてのみ動けばよく、ブラウザで開く必要がない。ローカルHTTPサーバを立てると、それだけのために次の面倒を抱え込む。

  • ポートの確保と衝突回避（移植元は3000固定で、塞がっていると起動できなかった）
  • 同じPC上の他プロセスからAPIを叩けてしまう。認証を持たないため、起動している間は無防備になる
  • プロセス内で完結する処理に、シリアライズ＋TCP往復という余計な段を挟むことになる

js_api なら webview.create_window(..., js_api=Api()) だけで、フロントから window.pywebview.api.<メソッド>() を Promise として呼べる。ポートもバインドも存在しないため、上の3点がまとめて消える。

js_api の実装上の注意

項目内容
APIの準備完了を待つwindow.pywebview はページ読込直後には存在しない。DOMContentLoaded ではなく pywebviewready イベントで初期化する。ここを間違えると起動直後だけ動かない
呼び出しスレッド各呼び出しはUIスレッドとは別のスレッドで実行される。SQLite接続は呼び出しごとに開いて閉じる（DB設計書 11章）
引数・戻り値JSONシリアライズ可能なものだけ。date や Decimal をそのまま返さない
エラー例外の伝わり方は版に依存するため頼らない。業務エラーは {"error": "…"} を返り値として返すと決め、JS側の薄いラッパーで throw する（12章）
HTMLの読込web/index.html を相対パスで指定する。PyInstallerで固める場合は sys._MEIPASS 起点の絶対パスに解決する
引き換えに失うもの

ブラウザの開発者ツールでフロントだけを単体デバッグする、という手が使えなくなる。設計上はそれで構わない ─ 画面の検証は .doc/mock/ の画面モックで行う。モックはダミーデータだけで動く静的ファイルであり、アプリ本体の機能ではない。

5. タスク一覧（SCR-02）

5-1. ヘッダ

左に「‹ リスト」の戻るボタン、中央にリスト名、右に件数。戻るとSCR-01へ復帰する。

5-2. 行の構成

位置内容
左丸いチェック。未完了＝灰の輪郭／完了＝青地にチェック。完了かどうかだけを表す
本文タスク内容。完了行は打消し線＋淡色
メタ行ジャンル名バッジ（ジャンル色の地）／カテゴリ名／日付／保留バッジ。幅が足りなければ折り返す

5-3. 表示と操作

項目仕様
日付表示本日・翌日・前日は「今日」「明日」「昨日」と語で出す。それ以外は M/D。期間タスクは M/D 〜 M/D。遅延している日付は赤の太字
並び順未完了 → 保留 → 完了、その中で no 昇順。ただし「実行済」だけは completed_at 降順（最近終えた順）
チェック操作即座に update_task。完了にする時は completed_at に現在時刻、戻す時は空文字。楽観的にUIを先行更新し、失敗時はロールバックしてトーストを出す
保留トグル保留中なら active へ、そうでなければ pending へ。完了中に押した場合は完了を解いて保留にし、completed_at を空にする。詳細シートを開かずに「いま手が付けられない」を記録するための導線
フラグトグルpriority を反転する
行タップSCR-03 の詳細を開く。トグル2つは当たり判定を分け、押しても詳細が開かないようにする
FAB右下固定。押すと新規作成モードでSCR-03が開く。ジャンル・カテゴリは現在の絞り込みを初期値とする
0件カード内に「該当するタスクはありません」を出す。カード自体は消さない
保留をどこで表すか

保留はメタ行のバッジ（文字）とトグル（操作）の2か所だけで表す。丸印は完了かどうかに専念させ、保留の色を混ぜない ─ 丸印をタップすると完了になるのに保留の色が出ていると、何を押したのか分からなくなる。役割を1つずつに割り当てる。

5-4. 適用中の絞り込み条件

絞り込みが効いている間、ヘッダ直下に条件をチップで並べる。各チップの × でその条件だけを外せる。条件が見えないまま件数が少ない状態は「データが消えた」と誤解される原因になるため、必ず可視化する。

モーダルの中に一覧ビューと編集ビューの2枚を持ち、data-mview で切り替える。ブラウザの prompt() / confirm() は使わない（理由は下の枠）。

7-1. 一覧ビュー

左にジャンル、右に選択中ジャンル配下のカテゴリ（移植元の「顧客・カテゴリ管理」と同じ2パネル構成）。幅が狭い時は縦積みになる。

7-2. 編集ビュー

ヘッダが「‹ 戻る ／ ◯◯を編集 ／ 保存」に変わる。削除もここに置く ─ 一覧の行にボタンを並べるより、対象を1つに絞ってから消す方が誤操作が減る。

項目ジャンルカテゴリ

名前の重複などで保存に失敗したときは編集ビューに留まる。一覧へ戻してしまうと、入力し直しになる。

prompt() / confirm() を使わない

WebView2 はスクリプトダイアログを出せるが、出るのはOSのそっけないダイアログで、アプリの見た目から浮く。prompt() は返るまでJSスレッドを止めるため、呼び出し側の処理も固まる。入力・確認はすべてモーダル内で行う。

削除の確認は、削除ボタンをその場で確認ボックス（「やめる」「削除する」）に差し替える2段階にする。別のダイアログを重ねない。

カテゴリ並び替えreorder_categories(genre_id, ids)genre_id も条件に入れ、他ジャンルのIDを渡されても書き換わらないようにする

ガントチャート形式。左列にタスク名、右に日付を横スクロールする帯を並べ、date_start〜date_end の範囲をバーで描画する（移植元 calendar.html の構造を踏襲）。

別ウィンドウで開く

カレンダーは横に長く、一覧と並べて見たい場面が多い。同じウィンドウでページ遷移すると一覧を見ながら日程を確認できないため、open_calendar() で別ウィンドウ（既定 1040×720）を作る。

  • 左上は「戻る」ではなく「閉じる」。close_calendar() がウィンドウを破棄する。
要素仕様
表示範囲既定は本日の前後30日（計61日）。1日＝34px
バージャンルの color で塗る。単日タスク（date_end 空）は1日分の幅。完了は不透明度を落とす
日付なしタスクカレンダーには表示しない（date_start が空の行は取得対象外）

土日列の背景を薄く色分けする
絞り込みジャンルとステータス（すべて／未完了／保留／完了）
ツールチップバーホバーで内容・ジャンル・カテゴリ・期間・ステータスを表示

9. スマートリスト判定ロジック

期間の求め方

  • 週は月曜始まり。today - timedelta(days=today.weekday()) が今週の月曜、+6日が日曜。
  • 「来週」は今週の月曜 +7日 〜 +13日。
  • 「今月」は当月1日〜当月末日。末日は calendar.monthrange(y, m)[1] で求める。
  • 「来月」は翌月1日〜翌月末日。12月の翌月は翌年1月として扱う。

タスク期間と対象期間の重なり判定

タスクの期間を [s, e]（e は date_end が空なら s と同値）、対象期間を [from, to] とすると、重なり条件は s <= to AND e >= from。日付はゼロ埋め 'YYYY-MM-DD' のため文字列比較がそのまま日付比較になる。

-- SQL上の表現
WHERE date_start != ''
  AND date_start <= :to
  AND (CASE WHEN date_end = '' THEN date_start ELSE date_end END) >= :from
空文字の落とし穴

日付未設定は ''（空文字）で保持する。空文字はあらゆる日付文字列より辞書順で小さいため、date_end >= :from をそのまま書くと未設定タスクが全期間にヒットしてしまう。必ず上記の CASE で単日に畳んでから比較し、かつ date_start != '' で未設定行を除外する。

各リストの条件

キー条件

today重なり判定 [本日, 本日]
tomorrow重なり判定 [本日+1, 本日+1]
this-week重なり判定 [今週月曜, 今週日曜]
next-week重なり判定 [来週月曜, 来週日曜]
this-month重なり判定 [当月1日, 当月末日]

上の条件を評価する前に、ステータスで絞る（10章。既定は未完了のみ）。そのため overdue と flagged の条件から status の判定が消えている。pending と completed の2つだけは、そのステータスを見るためのリストなので表示可否の対象外とする。

日付の基準時刻（注意）

「本日」はサーバ側（Python）のローカル日付で確定し、フロントでは計算しない。アプリを日をまたいで開きっぱなしにすると画面の「今日」が古くなるため、GET /api/counts のレスポンスに today を含め、フロントは前回値と変わっていたら一覧を再取得する。

移植元はキーワード検索しか持たなかった。本設計では上部バーの検索欄に加え、開閉式の絞り込みパネルを設ける。

ステータスの絞り込み（保留済・実行済）

既定では未完了だけを見せる。チェックを入れると、そのステータスだけに絞る。ほかの絞り込みと同じく、チェックを入れると「すべて」を母集合にした一覧へ移る。終わったものと止まっているものが常に混ざっていると、「いま手を付けるもの」が埋もれるため。

チェックの状態一覧に出るもの
どちらもOFF（既定）未完了のみ
保留済のみ だけON保留のみ
実行済のみ だけON完了のみ
どちらもON保留 ＋ 完了
  • スマートリスト「保留」「実行済」は対象外。そのステータスを見るためのリストなので、チェックを入れなくても中身が出る。ここを例外にしないと、既定で常に0件という無意味な状態になる。
  • スマートカードの件数にも同じ規則を効かせる。一覧が11件なのにカードが17と出ていると、数字の方が信用されなくなる。ジャンル／カテゴリ行の件数も同様。
  • ステータスを選ぶプルダウンは置かない。同じことを2つのUIで指定できると、どちらが効いているのか分からなくなる。「保留だけ」「完了だけ」を見たい場合はスマートリストの方を使う。
  • この2つは範囲を広げる操作なので、次項の「母集合を すべて に切り替える」対象から外す。「今日」を見ながら完了分も見たいだけのときに、リストごと移動してしまうのは意図と違う。

期限の範囲

「この日以降」「この日以前」を別々の条件として並べず、1つの範囲条件として扱う。単日タスクと期間タスクが混在するため、判定は9章の重なり判定をそのまま使う。

タスクの期間 [date_start, 終端日] が [due_from, due_to] と重なるか
  date_start <= due_to  AND  終端日 >= due_from
  ※ 終端日 = date_end が空なら date_start
  • 片側だけの指定でも成立する。欠けている側は無制限として扱う（due_to だけなら「その日まで」）。
  • 期限が未設定のタスク（date_start が空文字）は常に対象外。9章の空文字の落とし穴と同じ理由。
  • チップは「期限 2026-09-01 〜 2026-09-30」の1つにまとめる。× を押したら両方を同時に外す ─ 片方だけ残ると、利用者が意図していない絞り込みが残る。
  • 片側だけ指定されている場合、チップは空いている側を「指定なし」と表示する。

条件の組み合わせ方

  • 各条件は AND で結合する。空の条件は無視する。
  • スマートリスト／ジャンル選択による絞り込みとも AND で結合する。
  • 条件は入力を変えた時点で即反映する（「絞り込む」ボタンは置かない。パネルは絞り込みボタンで開閉し、「条件をクリア」だけを置く）。
  • 条件が1つでも入ると母集合を「すべて」に切り替える。「今日」を見ている状態で「来月の期限」を絞り込んでも0件になるだけで、利用者の意図と食い違うため。ステータス（保留済のみ・実行済のみ）も同じ扱い。

条件の可視化と解除

  • 適用中の条件は一覧の上に「ラベル 値 ×」のチップで並べる。条件が見えないまま件数が少ない状態は「データが消えた」と誤解される原因になる。
  • ジャンルのチップを外した時はカテゴリ条件も連動して外す（ジャンル外のカテゴリが残ると条件が矛盾するため）。
  • 「条件をクリア」はパネル内の条件だけを消し、キーワードは残す。キーワードは検索欄という別のUIに属しており、一緒に消えると操作の対応が取れなくなる。表示可否は既定（どちらもOFF）に戻す。
SQLの組み立て

条件は必ずプレースホルダで渡す。文字列連結でWHERE句を作らない。filters.py で条件の断片とパラメータ辞書を組み立て、' AND '.join(clauses) で結合する。

11. レスポンシブ設計

移植元の問題

electron-app.css には @media が1つも無く、本体は max-width: 640px の中央寄せ固定だった。そのため両端で破綻する。

  • 縮めると内容が押し出されて横スクロールが発生し、操作できなくなる。
  • 最大化しても中央に640pxの細い1列が残るだけで、左右が丸ごと余る。画面を広げた意味がない。

デスクトップアプリはユーザーが自由にウィンドウを変えるため、両方向を補う。

ブレークポイントレイアウト

表示の切替はCSSに寄せる

ダッシュボードと一覧は、狭い時は切替・広い時は併置になる。JSが style.display を直接いじると、幅が変わるたびに整合を取り直す羽目になる。JSは body の data-view を書くだけにし、出し分けはCSSに任せる。

/* 狭い時：切替 */
body[data-view="dashboard"] #task-list-view { display: none; }
body[data-view="list"]      #dashboard-view { display: none; }

/* 広い時：併置（同じ詳細度で上書きする） */
@media (min-width: 1024px) {
  body[data-view] #dashboard-view { display: block; }
  body[data-view] #task-list-view { display: flex; }
}
詳細度に注意

上書き側を #dashboard-view { display: block } と書くと効かない。body[data-view="list"] #dashboard-view（ID1＋属性1＋要素1）の方が詳細度が高く、メディアクエリの内側でも負ける。メディアクエリは詳細度を上げない。必ず同じ形のセレクタで上書きする。

詳細パネルの出し分け

同じ .detail-panel を、狭い時は position: fixed のボトムシート、広い時は grid の右列（position: relative）として使う。DOMは1つのままなので、幅が変わっても編集中の内容が失われない。

  • 広い時はオーバーレイを display: none にする。背後を覆う必要がないため。
  • 列は常に置いたままにする。未選択のとき列ごと消すと、タスクを選ぶたびに一覧の幅が変わってガタつく。::after でプレースホルダを出して幅を保つ。
  • 「右から滑り込む」演出は中身にだけかける（translateX(20px) → 0）。列そのものを動かすとレイアウトが揺れる。
  • FABは right: calc(var(--detail-w) + 24px) で詳細パネルの外へ逃がす。列幅をCSS変数で持つのは、この計算を1か所で済ませるため。

ブレークポイントに頼らない部分

スマートカードのグリッドは、640px以上では repeat(auto-fit, minmax(170px, 1fr)) で組む。ちょうど3列になり、幅が変わっても破綻しない。

スマホ幅では列数を固定する

auto-fit のままだと520px以下で2列に落ちる。11枚を3列で一望できることに意味があるため、520px以下は repeat(3, minmax(0, 1fr)) で3列に固定し、代わりにカード1枚あたりの余白・アイコン・文字を縮める。下限の360pxでも1枚106pxを確保でき、「フラグ付き」まで省略されずに収まる。

minmax(0, 1fr) にすること。1fr だけだと中身が列幅を押し広げ、横に溢れる。

縮小時に守ること

  • 横スクロールを絶対に出さない。カレンダーの日付グリッドだけは例外で、自身のコンテナ内で横スクロールする。
  • 長いテキストは省略記号で切る（ジャンル名、タスク名、カレンダーのラベル）。折り返して行の高さが崩れる方が読みにくい。
  • タップ対象は最小 28px 四方を確保する。
  • 見出しに flex: 1; min-width: 0 だけを与えない。縮みすぎて1文字ずつ折り返す。white-space: nowrap と併用し、縮むのではなく行ごと折り返させる。
  • 可変幅のペインには min-width: 0 を付ける。grid の 1fr は既定で min-width: auto のため、内容幅を下回れず隣の列を画面外へ押し出す。

起動時のウィンドウサイズ

初回は 390×820（スマホ相当）で開く。移植元のレイアウトがそのまま出る幅であり、まずは見慣れた形で立ち上がる方がよい。広い画面が要るかどうかは使う人が決めることで、こちらが最初から3カラムを押し付ける理由がない。

場面サイズ

保存されたサイズをそのまま使うと、大きいモニタで使った後に小さい画面へ移ったときウィンドウが画面外へはみ出す。主画面のサイズから余白を引いた値で頭打ちにし、下限も MIN_WINDOW で押さえる。値が壊れていた場合は初回サイズへ戻す。

最小化直後などの異常値（MIN_WINDOW 未満）は保存しない。次回の起動が潰れたウィンドウになるのを防ぐ。

min_size=(360, 480) で最小サイズを指定する。検証は 360×480（下限）／640×800（既定）／1000×800（シートのまま）／1024×800（3カラムの境界）／1600×900 の5点で行い、いずれも横スクロールが出ないことを確認する。とくに 1023px と 1024px の境界は、詳細の出方が切り替わるため必ず両側を見る。

13. CSVインポート

対象

temp\ 直下の *.csv。ファイル名に _imported_ を含むものは対象外。起動時に自動実行し、画面からも手動実行できる。

フォーマット

ジャンル,カテゴリ,開始日,終了日,内容,優先度,ステータス
プライベート,手続き,2026-09-20,,確定申告の書類をまとめる,高,未完了
学習,資格,2026-09-18,2026-09-25,参考書 第3章を読む,,完了
列必須変換規則
ジャンル○既存名と一致すればそのID。無ければ新規作成する
カテゴリ—該当ジャンル配下に無ければ新規作成。空欄なら NULL
開始日—YYYY-MM-DD / YYYY/M/D を受け付け、内部形式に正規化。解釈不能なら空文字
終了日—同上
内容○空行はスキップ
優先度—高 または ★ で 1、それ以外 0
ステータス—完了→completed、保留→pending、それ以外 active

処理手順

  1. 先にリネームする。元名_imported_YYYY-MM-DDTHH-MM-SS.csv へ改名し、成功したファイルだけを読む。理由は下の枠。
  2. ファイルを読む。エンコーディングは UTF-8（BOM付き含む）→ CP932 の順で試行する。Excelで保存したCSVはCP932になることが多いため。
  3. 標準ライブラリの csv.reader で解析する（移植元は自前のカンマ分割だったが、引用符内の改行を扱えなかった）。
  4. 1行目はヘッダとして読み飛ばす。
  5. 行ごとに上表の変換を行い、tasks へINSERTする。完了として取り込む行は completed_at に取込時刻を入れる。
  6. 重複判定：同一ジャンル内で内容が完全一致するタスクが既にあればスキップする（移植元は内容のみで全体重複判定していたため、別ジャンルの同名タスクを取り込めなかった）。
  7. ファイル全体を単一トランザクションで処理する。1件でも失敗したらそのファイルはロールバックし、次のファイルへ進む。
二重取込を防ぐ順序（重要）

移植元は取り込んでからリネームしていた。この順序だと、リネームに失敗した場合（ファイルがExcelで開かれている等）に取込済みのファイルが元の名前のまま残り、次の起動でもう一度取り込まれる。

本設計はリネームしてから読む。リネームできなければ何も取り込まずスキップするだけなので、取込履歴のテーブルを持たなくても二重取込は起きない。スキップしたファイルはログに残し、画面には「◯件のファイルを開けませんでした」と返す。

列構成が旧CSVと異なる

旧フォーマットは 日付,プロジェクト,ステータス,優先度,タスク内容（README記載の No,案件,日付,カテゴリ,内容,優先度,ステータス とも食い違っていた）。本設計ではジャンル・カテゴリを先頭に置く新フォーマットに統一する。旧CSVを取り込む必要がある場合は tools\ に変換スクリプトを用意する。

import webview

from backend import db
from backend.api import Api
from backend.config import FIRST_WINDOW, INDEX_HTML, MIN_WINDOW

WINDOW_SIZE_KEY = "window_size"
_last_size = None          # resized で受け取った最新サイズ


def _initial_size():
    """初回はスマホ相当。2回目以降は前回のサイズを復元する。"""
    saved = db.get_meta(WINDOW_SIZE_KEY, "")
    if not saved:
        return FIRST_WINDOW
    try:
        width, height = (int(v) for v in saved.split("x", 1))
    except ValueError:
        return FIRST_WINDOW
    # 画面構成が変わって収まらない場合に備えて丸める
    screen = _primary_screen()
    if screen:
        width  = min(width,  screen[0] - SCREEN_MARGIN)
        height = min(height, screen[1] - SCREEN_MARGIN)
    return max(width, MIN_WINDOW[0]), max(height, MIN_WINDOW[1])


def _on_resized(width, height):
    global _last_size
    _last_size = (int(width), int(height))


def main() -> int:
    db.init()                   # DDL適用・スキーマ版確認・初期ジャンル投入
    db.backup_on_startup()      # data/backup へ世代バックアップ

    width, height = _initial_size()
    window = webview.create_window(
        "タスク管理",
        str(INDEX_HTML),        # file:// で読む（HTTPではない）
        js_api=Api(),
        width=width, height=height,
        min_size=MIN_WINDOW,    # これ以下には縮められない（11章）
    )
    window.events.resized += _on_resized

    webview.start()             # ウィンドウを閉じるまでブロックする

    _save_size()                # 次回はこのサイズで開く
    db.checkpoint_and_close()   # WALを本体へ書き戻してから終了
    return 0

import sqlite3
from contextlib import contextmanager

from .config import DB_FILE


@contextmanager
def conn():
    """呼び出しごとに開いて閉じる。

    js_api の各呼び出しは別スレッドで実行されるため、接続を使い回さない。
    PRAGMA foreign_keys は接続ごとに必要（既定は無効）。
    """
    c = sqlite3.connect(DB_FILE)
    c.row_factory = sqlite3.Row
    c.execute("PRAGMA foreign_keys = ON")
    try:
        yield c
        c.commit()
    except Exception:
        c.rollback()
        raise
    finally:
        c.close()

backend/api.py（フロントの窓口）

import functools
import logging

from . import filters, repository

log = logging.getLogger(__name__)


class ApiError(Exception):
    """利用者に見せる業務エラー。"""


def public(fn):
    """例外を {"error": ...} に包む。

    pywebview の版によって例外の伝わり方が変わるため、例外に頼らず
    戻り値で表現すると決める（12章）。
    """
    @functools.wraps(fn)
    def wrapper(*args, **kwargs):
        try:
            return fn(*args, **kwargs)
        except ApiError as e:
            return {"error": str(e)}
        except Exception:
            log.exception("%s failed", fn.__name__)
            return {"error": "処理に失敗しました"}
    return wrapper


class Api:
    @public
    def list_tasks(self, params=None):
        params = params or {}
        clauses, args = filters.build(params)
        return repository.find_tasks(params.get("list", "all"), clauses, args)

    @public
    def create_task(self, body):
        if not (body.get("content") or "").strip():
            raise ApiError("タスク内容は必須です")
        if not body.get("genre_id"):
            raise ApiError("ジャンルは必須です")
        s, e = body.get("date_start", ""), body.get("date_end", "")
        if s and e and s > e:
            raise ApiError("終了日は開始日以降にしてください")
        return repository.create_task(body)

    @public
    def delete_genre(self, genre_id):
        remaining = repository.count_tasks_of_genre(genre_id)
        if remaining:
            raise ApiError(f"このジャンルにタスクが{remaining}件残っています")
        repository.delete_genre(genre_id)
        return {"ok": True}

    @public
    def counts(self):
        return repository.counts()

import calendar
from datetime import date, timedelta

# 対象期間 [from, to] を返す。日付を持たないリストは None を返す。
def period_of(key: str, today: date):
    if key == "today":
        return today, today
    if key == "tomorrow":
        d = today + timedelta(days=1)
        return d, d
    if key in ("this-week", "next-week"):
        monday = today - timedelta(days=today.weekday())   # 月曜始まり
        if key == "next-week":
            monday += timedelta(days=7)
        return monday, monday + timedelta(days=6)
    if key in ("this-month", "next-month"):
        y, m = today.year, today.month
        if key == "next-month":
            y, m = (y + 1, 1) if m == 12 else (y, m + 1)
        return date(y, m, 1), date(y, m, calendar.monthrange(y, m)[1])
    return None

backend/filters.py（絞り込み条件の組み立て）

def build(params, apply_visibility=True) -> tuple[list[str], dict]:
    """絞り込み条件から WHERE 句の断片とパラメータ辞書を作る。
    値は必ずプレースホルダで渡す（文字列連結しない）。

    apply_visibility=False は「保留」「実行済」リスト用。
    そのステータスを見るためのリストなので表示可否を効かせない（10章）。
    """
    clauses, args = [], {}

    if params.get("q"):
        clauses.append("(content LIKE :q OR result LIKE :q)")
        args["q"] = f"%{params['q']}%"

    # ステータスの絞り込み。既定は未完了だけ、チェックがあればそれだけ（10章）
    shown = []
    if params.get("show_pending") == "1":
        shown.append("pending")
    if params.get("show_completed") == "1":
        shown.append("completed")
    if apply_visibility:
        shown = shown or ["active"]
        # IN 句もプレースホルダで組む
        keys = [f":show{i}" for i in range(len(shown))]
        clauses.append(f"status IN ({', '.join(keys)})")
        args.update({k.lstrip(':'): v for k, v in zip(keys, shown)})

    for key in ("genre_id", "category_id", "priority"):
        if params.get(key):
            clauses.append(f"{key} = :{key}")
            args[key] = params[key]

    # 期限の範囲。2入力で1条件。片方だけでも成立させる（10章）
    due_from, due_to = params.get("due_from"), params.get("due_to")
    if due_from or due_to:
        clauses.append("date_start != ''")          # 期限なしは常に対象外
        if due_to:
            clauses.append("date_start <= :due_to")
            args["due_to"] = due_to
        if due_from:
            clauses.append(
                "(CASE WHEN date_end = '' THEN date_start ELSE date_end END)"
                " >= :due_from")
            args["due_from"] = due_from

    return clauses, args

16. 旧実装からの変更点

アーカイブを廃止した

移植元は完了タスクを tasks_archived テーブルへ物理移動する「アーカイブ」を持っていた。本設計ではこれを廃止する。

  • 「実行済」と機能が重複している。スマートカードの「実行済」で完了タスクだけを一覧でき、未完了リストに混ざることもない。アーカイブが別に解決している問題が無い。
  • 性能上の必要がない。個人用途の数千件規模では、status のインデックス付き絞り込みは瞬時に終わる。テーブルを分ける理由が出てこない。
  • 複雑さがバグを生んでいた。2テーブル化に伴いジャンル名のスナップショット保持・復元時のID再解決・no の再採番が必要になる。実際、移植元の復元SQLは result と date_end をINSERT対象から落としており、復元するとメモと終了日が消えていた。

代わりに completed_at を持たせ、「実行済」を完了日時の降順で並べる。移植元は完了日時を記録していなかったため、これは機能として増える。古い完了分を消したい場合は delete_completed(before) で足りる。

HTTPサーバを廃止した

移植元は Express でポート3000を開き、Electron からもブラウザからも同じ画面を開ける構成だった。本アプリはアプリとしてのみ動けばよいため、pywebview の js_api でプロセス内呼び出しに置き換える。ポートの確保・衝突回避、同一PC上の他プロセスからAPIを叩かれる隙、TCP往復のオーバーヘッドがまとめて無くなり、依存ライブラリも pywebview 1つだけになる（詳細は1章）。
