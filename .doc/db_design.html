1. 概要・方針

単一ユーザーのローカルアプリのため user_id は持たない。DBファイルはアプリ配下 data/todo.db に置き、これ1つを退避すれば全データのバックアップとなる。

  • 分類軸の変更：旧DBの tasks.project（顧客名を文字列で保持）を廃止し、genres（ジャンル）テーブルへ正規化する。旧 tasks.category（文字列）も categories テーブルへ正規化する。
  • 2階層構造：カテゴリは必ず1つのジャンルに属する（categories.genre_id）。タスクはジャンル必須・カテゴリ任意とする。
  • 整合性：旧実装は顧客名リネーム時に UPDATE tasks SET project=… で文字列を追従させていたが、ID参照にすることでこの追従処理そのものを不要にする。
  • テーブルは tasks 1本：完了タスクを別テーブルへ退避する仕組み（アーカイブ）は持たない。理由は下の枠を参照。
  • 日付は TEXT の 'YYYY-MM-DD' 形式で保持（SQLiteに日付型は無い。文字列の辞書順＝時系列順となる形式を採用）。
  • 日時は TEXT のISO8601（'YYYY-MM-DDTHH:MM:SS'、ローカル時刻）で保持。
  • 論理削除は使わない。ジャンル／カテゴリの削除は 11章の参照規則で扱う。
アーカイブを持たない理由

旧実装は完了タスクを tasks_archived へ物理移動していた。目的は「一覧が完了タスクで溢れるのを防ぐ」ことだが、本アプリではこれを採らない。

  • 「実行済」で同じことができる。status = 'completed' で絞り込めば完了分だけを一覧でき、未完了リストに混ざることもない。アーカイブは機能として重複している。
  • 性能上の必要がない。個人用途で想定されるのは数千件規模であり、SQLiteにとって status のインデックス付き絞り込みは瞬時に終わる。分割する理由が性能面から出てこない。
  • 複雑さがバグを生んでいた。2テーブル化に伴い、ジャンル名のスナップショット保持・復元時のID再解決・復元先の no 再採番が必要になる。実際に旧実装の復元SQLは result と date_end をINSERT対象から落としており、復元するとメモと終了日が消えていた。

代わりに completed_at（完了日時）を持たせ、「実行済」を完了日時の降順で並べる。旧実装では「いつ終えたか」が記録されていなかったため、これは機能として増える。古い完了分を本当に消したい場合は、完了日時を条件にした一括削除で足りる。

注意　tasks.no（表示用の連番）は旧実装を踏襲して残すが、主キーではない。並び替え・手動採番の都合で重複・欠番が起こりうるため、一意制約は付けない。

関連はすべて外部キー制約付き。app_meta は他テーブルと関連を持たない独立したテーブル。

3. genres（ジャンル）

旧DBの customers に相当。仕事用の顧客区分の代わりに、私用の大分類（例：プライベート／学習／趣味／家事）を持つ。

4. categories（カテゴリ）

ジャンル配下の小分類。旧DB categories の customer_id を genre_id に置換したもの。

カラム型制約既定値説明
idINTEGERPKAUTOINCREMENTカテゴリID
genre_idINTEGERFK NOT NULL—→ genres.id　ON DELETE CASCADE
nameTEXTNOT NULL—カテゴリ名
sort_orderINTEGERNOT NULL0同一ジャンル内の表示順
created_atTEXTNOT NULLISO8601作成日時

複合一意制約：UNIQUE(genre_id, name)。異なるジャンルであれば同名カテゴリを作れる（例：「学習／読書」と「趣味／読書」）。

本アプリで唯一のトランザクションテーブル。完了タスクもここに残り続ける。

completed_at の更新規則（要注意）

completed_at は「完了でなかったものが完了になった瞬間」にだけ打つ。既に完了のタスクを編集保存しただけで打ち直すと、「実行済」の並び順が編集順になってしまい、いつ終えたかが分からなくなる。完了以外へ戻した時は空文字でクリアする。

期間タスクの扱い（要注意）　date_end が空文字のときは単日タスクとして date_start のみを判定に使う。date_end がある場合、スマートリストの期間判定は「date_start〜date_end の範囲が対象期間と重なるか」で行う（詳細設計書 9章）。

7. app_meta（スキーマ管理）

旧実装は ALTER TABLE を try/catch で握りつぶす方式だったが、本設計ではスキーマ版数を明示管理する。

カラム型制約説明
keyTEXTPKキー名。'schema_version' / 'window_size'
valueTEXTNOT NULL値

起動時に schema_version を読み、コード側の期待版数より小さければ順にマイグレーション関数を適用して版数を更新する。初回作成時は '1' を書き込む。

キー値の例用途
schema_version'1'DDLの版数
window_size'900x700'前回閉じたときのウィンドウサイズ。未設定なら初回として 390×820 で開く（詳細設計書 11章）

8. 区分値（コード定義）

値表示意味

移植元の詳細画面には「保留」の選択肢があったが、保留タスクを一覧する手段が用意されておらず、切り替えるにも毎回詳細画面を開く必要があった。保留にすると事実上見失う状態だったため、本設計ではスマートリストに「保留」を追加し、さらに一覧の行から1タップで切り替えられるようにする。

各リストは上の条件を評価する前に、既定で保留（pending）と完了（completed）を落とす。絞り込みの「保留済を表示」「実行済を表示」で足す（詳細設計書 10章）。「保留」「実行済」の2リストだけは対象外。

9. DDL全文

PRAGMA foreign_keys = ON;
PRAGMA journal_mode = WAL;

CREATE TABLE IF NOT EXISTS genres (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    name        TEXT    NOT NULL UNIQUE,
    color       TEXT    NOT NULL DEFAULT '#007AFF',
    sort_order  INTEGER NOT NULL DEFAULT 0,
    created_at  TEXT    NOT NULL
);

CREATE TABLE IF NOT EXISTS categories (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    genre_id    INTEGER NOT NULL,
    name        TEXT    NOT NULL,
    sort_order  INTEGER NOT NULL DEFAULT 0,
    created_at  TEXT    NOT NULL,
    FOREIGN KEY (genre_id) REFERENCES genres(id) ON DELETE CASCADE,
    UNIQUE (genre_id, name)
);

CREATE TABLE IF NOT EXISTS tasks (
    id           INTEGER PRIMARY KEY AUTOINCREMENT,
    no           INTEGER NOT NULL DEFAULT 0,
    genre_id     INTEGER NOT NULL,
    category_id  INTEGER,
    content      TEXT    NOT NULL,
    result       TEXT    NOT NULL DEFAULT '',
    date_start   TEXT    NOT NULL DEFAULT '',
    date_end     TEXT    NOT NULL DEFAULT '',
    priority     INTEGER NOT NULL DEFAULT 0 CHECK (priority IN (0, 1)),
    status       TEXT    NOT NULL DEFAULT 'active'
                         CHECK (status IN ('active', 'pending', 'completed')),
    completed_at TEXT    NOT NULL DEFAULT '',
    created_at   TEXT    NOT NULL,
    updated_at   TEXT    NOT NULL,
    FOREIGN KEY (genre_id)    REFERENCES genres(id)     ON DELETE RESTRICT,
    FOREIGN KEY (category_id) REFERENCES categories(id) ON DELETE SET NULL
);

CREATE TABLE IF NOT EXISTS app_meta (
    key   TEXT PRIMARY KEY,
    value TEXT NOT NULL
);

CREATE INDEX IF NOT EXISTS idx_tasks_genre     ON tasks(genre_id, status);
CREATE INDEX IF NOT EXISTS idx_tasks_category  ON tasks(category_id);
CREATE INDEX IF NOT EXISTS idx_tasks_date      ON tasks(date_start, date_end);
CREATE INDEX IF NOT EXISTS idx_tasks_status    ON tasks(status, no);
CREATE INDEX IF NOT EXISTS idx_tasks_completed ON tasks(completed_at DESC);
CREATE INDEX IF NOT EXISTS idx_cat_genre       ON categories(genre_id, sort_order);

10. 旧DBからの移行

移行元：C:\Windows11\work\todo_app\data\tasks.db（better-sqlite3 が作成したSQLiteファイル）。同じSQLiteなので ATTACH で直接読める。

旧 tasks.project は顧客名（GP／らくすむ／セオリアファーマ／その他）であり、私用アプリでは意味を持たない。下記SQLは名前をそのまま暫定ジャンルとして取り込む（移行後に画面上で改名・統合する前提）。過去データを引き継がず新規に作り直す場合、本節は不要。

旧 tasks_archived の行は完了タスクとして tasks に取り込む。アーカイブという区分自体を持たないため、通常の完了タスクと同じ扱いになる。

-- tools/migrate_from_old.py が実行するSQLの骨子
ATTACH DATABASE 'C:\Windows11\work\todo_app\data\tasks.db' AS old;

-- 1) 旧 project を暫定ジャンルとして取り込む（tasks と tasks_archived の両方から）
INSERT OR IGNORE INTO genres (name, color, sort_order, created_at)
SELECT DISTINCT CASE WHEN project IS NULL OR project = '' THEN 'その他' ELSE project END,
       '#007AFF', 0, datetime('now', 'localtime')
FROM (SELECT project FROM old.tasks UNION SELECT project FROM old.tasks_archived);

-- 2) 旧 category（文字列）を対応ジャンル配下のカテゴリとして取り込む
INSERT OR IGNORE INTO categories (genre_id, name, sort_order, created_at)
SELECT DISTINCT g.id, x.category, 0, datetime('now', 'localtime')
FROM (SELECT project, category FROM old.tasks
      UNION SELECT project, category FROM old.tasks_archived) x
JOIN genres g
  ON g.name = CASE WHEN x.project IS NULL OR x.project = ''
                   THEN 'その他' ELSE x.project END
WHERE x.category IS NOT NULL AND x.category != '';

-- 3) タスク本体を移送（文字列 → ID解決）
INSERT INTO tasks (no, genre_id, category_id, content, result,
                   date_start, date_end, priority, status, completed_at,
                   created_at, updated_at)
SELECT t.no, g.id, c.id, t.content, COALESCE(t.result, ''),
       COALESCE(t.date, ''), COALESCE(t.date_end, ''),
       COALESCE(t.priority, 0),
       CASE WHEN t.status = 'completed' THEN 'completed'
            WHEN t.status = 'pending'   THEN 'pending'
            ELSE 'active' END,
       -- 旧DBに完了日時は無い。完了済みは updatedAt で代用する
       CASE WHEN t.status = 'completed'
            THEN COALESCE(t.updatedAt, t.createdAt, '') ELSE '' END,
       COALESCE(t.createdAt, datetime('now', 'localtime')),
       COALESCE(t.updatedAt, t.createdAt, datetime('now', 'localtime'))
FROM old.tasks t
JOIN genres g
  ON g.name = CASE WHEN t.project IS NULL OR t.project = ''
                   THEN 'その他' ELSE t.project END
LEFT JOIN categories c ON c.genre_id = g.id AND c.name = t.category
WHERE t.content IS NOT NULL AND t.content != '';

-- 4) 旧アーカイブは「完了タスク」として同じ tasks へ取り込む
INSERT INTO tasks (no, genre_id, category_id, content, result,
                   date_start, date_end, priority, status, completed_at,
                   created_at, updated_at)
SELECT a.no, g.id, c.id, a.content, COALESCE(a.result, ''),
       COALESCE(a.date, ''), COALESCE(a.date_end, ''),
       COALESCE(a.priority, 0), 'completed',
       -- アーカイブ日時を完了日時として使う
       COALESCE(a.archivedAt, a.updatedAt, a.createdAt, ''),
       COALESCE(a.createdAt, datetime('now', 'localtime')),
       COALESCE(a.updatedAt, a.createdAt, datetime('now', 'localtime'))
FROM old.tasks_archived a
JOIN genres g
  ON g.name = CASE WHEN a.project IS NULL OR a.project = ''
                   THEN 'その他' ELSE a.project END
LEFT JOIN categories c ON c.genre_id = g.id AND c.name = a.category
WHERE a.content IS NOT NULL AND a.content != '';

-- 5) no を振り直す（3と4で重複しているため）
UPDATE tasks SET no = (SELECT COUNT(*) FROM tasks t2 WHERE t2.id <= tasks.id);

DETACH DATABASE old;
移行時の注意
  • 移行は必ず新規の空 todo.db に対して1回だけ実行する。再実行すると 3) 4) が重複投入される（INSERT OR IGNORE が効くのは 1) 2) のみ）。実行前に SELECT COUNT(*) FROM tasks が0であることを確認する。
  • 旧 tasks と tasks_archived で no が重複しているため、5) で必ず振り直す。これを省くと一覧の並びが崩れる。
  • 旧 tasks.date はCSV取込由来で書式が混在している可能性がある。移行後に点検する：
    SELECT id, date_start FROM tasks WHERE date_start != '' AND date_start NOT GLOB '[0-9][0-9][0-9][0-9]-[0-9][0-9]-[0-9][0-9]';
  • 旧DBは customers / categories マスタを持つが、タスク側は文字列参照だったため両者が食い違っている場合がある。上記SQLはタスクの実データ側を正とする。
  • 移行前に旧 tasks.db を別名でコピーしておく。ATTACH は読み取りのみだが、誤操作に備える。

11. SQLite固有の実装事項

外部キーの有効化（必須）

SQLiteは既定で外部キー制約が無効。接続ごとに PRAGMA foreign_keys = ON を発行しないと ON DELETE CASCADE も RESTRICT も効かない。接続生成処理（db.get_conn()）の中で必ず実行する。

スレッド安全性

js_api の各呼び出しは、UIスレッドとは別のワーカースレッドで実行される。sqlite3.Connection は既定で生成スレッド以外から使えないため、呼び出しごとに接続を開いて閉じる方針とする（contextmanager で包む）。check_same_thread=False で接続を使い回す実装は競合の原因になるため採らない。

行アクセス

conn.row_factory = sqlite3.Row を設定し、dict(row) でJSON化する。タプル添字参照はカラム追加時に壊れるため使わない。

型・制約のマッピング

論理型SQLite型備考
IDINTEGER PRIMARY KEYAUTOINCREMENT 指定でIDの再利用を防ぐ
真偽値INTEGER (0/1)SQLiteにBOOLEAN型は無い。API境界でbool変換する
日付TEXT 'YYYY-MM-DD'辞書順比較がそのまま日付比較になる
日時TEXT ISO8601Python側は datetime.now().isoformat(timespec='seconds')

WALモードとバックアップ

journal_mode=WAL を有効にすると todo.db-wal / todo.db-shm が併存する。手動バックアップで todo.db だけコピーすると未反映分を失うため、アプリ終了時に PRAGMA wal_checkpoint(TRUNCATE) を実行してから閉じる。

参照整合性・削除規則の方針（要注意）

操作規則挙動
ジャンル削除（タスク）RESTRICT配下にタスクが1件でも残っていると削除が失敗する。UI側で「タスクを別ジャンルへ移動してから削除」を促す
ジャンル削除（カテゴリ）CASCADE配下カテゴリは同時に削除される
カテゴリ削除SET NULLそのカテゴリを持つタスクは「なし」になる（タスク自体は消えない）
ジャンル／カテゴリの改名—ID参照のためタスク側の更新は不要
ジャンル削除を CASCADE にしない理由

CASCADEにすると、ジャンルを1つ消した拍子に配下のタスクが黙って全部消える。個人のタスク履歴を誤操作で失う影響が大きいため、明示的に移動させてからでないと消せないようにする。
