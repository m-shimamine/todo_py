# 標準章構成

案件に無い章は落とす。足りなければ足す。番号は詰め直す。

## DB設計書（db_design.html）

| # | 章 | 中身 |
|---|---|---|
| 1 | 概要・方針 | 誰のデータか、マルチテナントか単一ユーザーか、日付・日時・真偽値の保持形式、論理削除の方針、正規化の方針。**この案件固有の判断だけを書く**（一般論は不要） |
| 2 | ER図 | インラインSVG。実線＝FK制約あり、破線＝制約なしの関連。図の下に凡例を1文 |
| 3〜 | テーブル定義 | 1テーブル1章。冒頭に「旧DBの◯◯に相当」など位置づけを1文。表は5列で統一 |
| — | 区分値（コード定義） | status / type / 権限などの取り得る値と表示名。複数あれば横並びの小表に分ける |
| — | インデックス設計 | インデックス名 / 対象 / 用途。件数規模の想定を1文添える |
| — | DDL全文 | コピーして流せる完全なDDL。`PRAGMA` や `CREATE INDEX` も含める |
| — | 移行 | 移植・リプレース時のみ。移行SQLと**再実行時の危険性**を明記 |
| — | DB固有の実装事項 | そのDBでハマる箇所。接続設定、スレッド安全性、型マッピング、削除規則の一覧 |

テーブル定義の表（5列で固定）：

| カラム | 型 | 制約 | 既定値 | 説明 |
|---|---|---|---|---|
| id | INTEGER | PK | AUTOINCREMENT | … |

制約欄のバッジ：`<span class="pk">PK</span>` `<span class="fk">FK</span>` `<span class="nn">NOT NULL</span>`

## 詳細設計書（detailed_design.html）

| # | 章 | 中身 |
|---|---|---|
| 1 | システム構成 | 構成図（SVG）＋**技術選定と理由**の表＋採らなかった選択肢とその理由 |
| 2 | ファイル構成 | ディレクトリツリー。移植なら末尾に「移植元 → 移植先」の対応を併記 |
| 3 | 画面一覧・遷移 | 画面ID（SCR-01…）／画面名／ファイル／概要の表＋遷移図（SVG） |
| 4〜 | 画面ごとの仕様 | 1画面1章。ワイヤーフレーム（SVG）＋ペイン/項目ごとの仕様表 |
| — | API設計 | 機能グループごとに表を分ける。Method / パス / パラメータ / 説明。必須は `*` 印。末尾にレスポンス例（JSON）とHTTPステータスの使い分け |
| — | 主要ロジック | 日付計算・集計・自動生成など。**SQLやコードの断片を必ず載せる**。散文だけにしない |
| — | 実装サンプル | エントリポイント・接続管理・ルート例など、骨格が分かる最小限のコード |
| — | 起動・配布 | 依存ライブラリ、セットアップ手順、起動スクリプト、前提環境 |
| — | 旧実装からの変更点 | 移植・リプレース時は必須。分類 / 旧 / 新 の3列。最後に「そのまま踏襲するもの」を1段落 |

## 画面仕様表の項目（画面ごとの章で使う）

入力フォームがある画面：

| 項目 | 入力 | 仕様 |
|---|---|---|

一覧・操作が中心の画面：

| 要素 | 仕様 |
|---|---|

「仕様」欄には**具体値**を書く。「適切にバリデーションする」ではなく
「必須。空なら保存ボタンを無効化」と書く。
